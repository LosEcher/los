# 跨平台"可部署内容标识"设计

Date: 2026-10-11
缘起：一天内连修两个"判据比事实弱"的缺陷（macOS 剪枝不收敛、Windows verify 为崩溃循环背书）。
两者背后是同一个结构问题：**机队收敛的唯一判据（内容摘要）只有一个 bash 实现，且它的文件清单
内联在一个函数里**。本文给出方案。

## 0. 结论

把"文件选择 + 逐文件摘要 + 汇总摘要"抽成一个 Node 模块
（`tools/deployable-content.mjs`），作为**唯一实现**；bash 与 PowerShell 都只是调用者。
Node 是机队已有的硬依赖 —— 执行器本身就是一个 Node 进程，每台节点上都有 `node`。

顺带得到两件现在缺失的能力：Windows 节点第一次有了内容标识；"某台节点的摘要为什么不一样"
从"手抄 20 行 find"变成一条 `--files` 对比命令。

## 1. 现状与三处已发生的代价

内容摘要（`tools/los.sh build-version`，形如 `0.1.0+b580057c47487`）是：

- 部署下发的**版本戳**（写进 `/opt/los/.env` 与 `C:\los\.env`）；
- 协调器判断"这台已经收敛、可以跳过"的**唯一内容判据**；
- runbook 里"stamp 不能证明磁盘上是哪份代码，摘要才能"的那个**证据面**。

它现在的形态是一个内联在 bash 函数 `resolve_local_runtime_version` 里的管道：
`find … 20 行排除规则 … | LC_ALL=C sort | xargs shasum -a 256 | shasum -a 256 | cut -c1-12`。

| 代价 | 实证 |
| --- | --- |
| **Windows 没有任何内容标识** | `tools/deploy-drivers/windows-service.sh` 的 verify 只能断言"服务 Running + `.env` 已盖章 + 一个探针文件存在"；协调器对 Windows 的 digest 永远是 `<no-response>`/`n/a`，于是**每轮滚动都会重跑驱动**，且 `desktop-srsbe20` 的"stamped but not converged"只能靠人工发现 |
| **诊断要手抄实现** | 2026-10-11 M3 事故定位时，我不得不手写一份 20 行的 `find … | xargs shasum -a 256` 才能在两侧逐文件比对；而"两侧文件集合差在哪"正是那次的判决性证据（唯一差 1 个文件） |
| **清单不可复用** | 排除清单是**唯一真源但只能被这一个函数使用**。任何第二个消费者（Windows 驱动、看板、审计脚本）要么抄一份，要么不做 —— 现在是"不做" |

这三条不是风格问题：本仓已经两次被同一句话打中 —— **"两套实现必然漂移"**
（`docs/operations/2026-10-07-fleet-rollout-design.md` §2 缺陷 2）。

## 2. 备选方案

| # | 方案 | 做法 | 判决 |
| --- | --- | --- | --- |
| A | 维持现状 + Windows 不判定 | Windows 继续只有"服务/戳/探针"三条 | **击败**：无内容证据；每轮无谓重跑；把"进程在跑"的证据当成了"内容对"的证据（正是 srsbe20 那个假阳性） |
| B | PowerShell 复刻一份 | 在 Windows 驱动里用 `Get-FileHash` 复刻 find 的剪枝/排除/排序/格式 | **击败**：两份实现必然漂移。而且摘要对**任何**一处差异都敏感 —— 路径分隔符（`\` vs `/`）、排序口径（字节序 vs UTF-16）、行尾、是否跟随符号链接，任一处不同就是"永不收敛"，且症状与"内容真的不同"无法区分。这恰是 M3 那次的形态 |
| C | 网关生成清单下发，各平台各算 | 清单单一真源（网关生成），摘要仍两份实现 | **击败**：只是把 B 的风险从"清单+算法"缩到"算法"；而且清单与树可能不同步（下发失败时无声地算出一个"看起来对"的摘要） |
| **D** | **Node 单一实现（选定）** | 一个模块同时提供"清单"与"摘要"，bash / PowerShell / 网关都调用它 | **胜出**：一份实现、三平台逐位一致、顺带获得 `--files` 诊断面、新平台接入成本≈0（有 node 就能算） |
| E | 节点在心跳里自报摘要 | 注册表成为收敛真源 | **记为第二阶段**（§6）：依赖 D 先让节点能算摘要；本阶段不做 |

D 的关键前提已核实：网关 `v24.14.0`，`node34` `v24.16.0`，M3 `v24.14.0`，
`win-los` `v24.16.0` —— **每台都有 Node 24**，`fs`/`crypto` 内置模块足够，不引入新依赖。

## 3. 决策与不变量

**D1 单一实现**：`tools/deployable-content.mjs`
- 子命令：`--digest`（默认）、`--files`、`--json`
- 版本串格式**不变**：`<base>+b<12hex>`，`base` 取 `packages/executor/package.json` 的 `version`
- 摘要算法与旧 bash **逐位一致**（等价性证明见 §5）：
  逐文件 `sha256` → 按**路径字节序**排序 → 以 `"<hash>  <path>\n"` 拼文本 → 整串 `sha256` → 取前 12 位
- 文件选择语义与 `find` 对齐：
  剪掉目录 `node_modules`/`dist`/`.turbo`/`.los`/`.los-runtime`（任意深度）；
  只收**常规文件**（`find -type f` 不收符号链接）；排除 `*.tsbuildinfo`/`.DS_Store`/`._*`；
  排除 13 个"只在网关跑"的脚本；再加 5 个根 manifest
- 路径统一用 `/`，排序按字节（两台平台的 `sort` 口径一致）

**D2 消费方只调用不复制**
- `tools/los.sh build-version` 变成一层壳（`node … --digest`），`--files` 透传
- Windows 驱动新增 `digest` 子命令（`node <home>\tools\deployable-content.mjs --digest`）
- 协调器对 Windows 的 digest 走驱动，于是它和 Linux/macOS 用**同一个判据**

**D3 诊断面**：`--files` 输出摘要覆盖的**确切文件清单**。这是 M3 那次最耗时的一步
（当时靠手抄 find 才发现"只多一个文件"）。

**D4 不引入新依赖**：只用 Node 内置模块。

**D5 迁移是一次性的，且不允许走捷径**：新模块与改动后的 `los.sh` 都在摘要覆盖范围内
⇒ 目标摘要必然变化 ⇒ 机队要滚一轮。**不允许**为了让目标不变而把新模块排除在摘要之外 ——
那会让"节点实际执行的内容"与"摘要"脱钩，等于把标识降级成口号。

**D6 摘要的语义边界不变**：仍然只覆盖"节点实际执行/加载的内容"（网关侧脚本继续排除）。
排除清单从一个 bash 函数搬到一个 Node 模块，**内容逐条不变**。

## 5. 验收：先证明等价，再切换

| 判据 | 方法 |
| --- | --- |
| **E1 等价性（切换前）** | 同一份文件清单下，Node 的 12 位摘要与旧 bash 管道**逐位相同**；`--files` 与旧 `find` 管道输出**集合相等**（预期唯一差集 = 新模块自身） |
| **E2 跨平台一致性** | Windows 节点上 `digest` 的输出 == 网关目标 —— 这是"Windows 第一次有内容标识"的判据 |
| **E3 负向控制** | 改一个被覆盖的文件 ⇒ 摘要变；在 `dist/`/`node_modules/` 下增删文件 ⇒ 摘要**不变**（证明剪枝语义被继承） |
| **E4 收敛判据** | `--plan` 对 Windows 从 `n/a` 变成真摘要，且收敛后能**跳过**（不再每轮重跑驱动） |
| **E5 迁移** | canary 一台 Linux → 摘要 == 新目标 → 其余（含 macOS 与两台 Windows） |

E1 的顺序不可颠倒：**没有等价性证明就不切换**。理由是这个改动的失败形态是"全机队永不收敛"，
而它的症状与"内容真的不同"长得一模一样（M3 那次的教训）。

### 5.1 实测结果（2026-10-11）

| 判据 | 结果 |
| --- | --- |
| **E1 清单等价** | `--files` 与旧 `find` 管道输出**完全一致**：1456 = 1456，diff 为空 `[E]` |
| **E1 摘要等价** | 同一份显式清单下，Node 与旧 bash 管道给出逐位相同的 `6b9c7fb63fee` `[E]` |
| **跨平台/跨 Node 版本** | 同一棵被覆盖的树：macOS + Node 24 与 Linux(Node34) + Node 22 都得到 `0.1.0+b27e4c55025c2` `[E]` |
| **E3 负向控制** | 固化在 `tools/deployable-content.test.mjs`（`pnpm check:deployable-content`，6/6）：golden 值钉格式；改动被覆盖文件必变摘要；剪枝目录/网关脚本/`*.tsbuildinfo`/符号链接都不影响摘要 `[E]` |
| **E5 迁移** | canary（vultr）→ 摘要 == 新目标 → 其余 7 台；8/8 `online` 且都在 `0.1.0+b27e4c55025c2` `[E]` |
| **E2/E4 Windows** | 两台 Windows 现在各自算出真摘要并**命中"already converged — skip"**；此前是 `<no-response>`/`n/a`、每轮重跑驱动 `[E]` |

### 5.2 落地过程暴露的三件事（都不是摘要本身的缺陷，而是它照出来的）

1. **Windows 没有剪枝 ⇒ 节点内容从来就不是目标内容。** 摘要一落地，两台 Windows 立刻报出各自
   不同、且都不等于目标的数。用 `--files` 两侧 diff（正是 D3 提供的诊断面）定位：win-los 45 个、
   srsbe20 14 个陈旧文件（被上游删除的源文件、有人手工解开的 nssm 源码树、`packages/*/pkg.tar`），
   **缺失 0 个**。⇒ Windows 驱动补剪枝（清单来自 `tar` 自己，`deploy-to-remote.sh tarball` 顺带落下
   `*.list`），两台随即收敛。
2. **服务包装器 `nssm.exe` 原本躺在被部署的树里。** 剪枝把它判为陈旧 —— 只因执行中的文件被占用
   才没删掉；**若剪枝发生在服务停止期间，节点会被删成"起不来"**。已把它移到树外的
   `C:\los-node\`（`reg add ImagePath` + 启停验证），树内那份随剪枝清掉。
   教训：**节点本地基础设施不要放在被部署的树内**，否则"树 == 下发内容"这条不变量不成立。
3. **目标摘要取自网关的*工作树*，所以未提交的改动会移动目标。** 实测：另一个会话在同一 checkout
   里改了两个 `packages/agent` 源文件，摘要在两次探测之间就变了（plan 表头与 local 节点自相矛盾）。
   危害不止"数字变了"：**可能把别人的未完成改动滚到全机队**。已在编排器里加显式警告
   （列出被覆盖范围内的脏文件 + 说明目标是脏树快照；只警告不阻断，因为操作者可能有意滚未提交修复）。

第 3 条同时是**第二阶段的最强动机**：期望态应该取自**已合并的修订**，而不是取自一份随时可能被
别的进程改写的活工作树；节点自报摘要 + 注册表成为收敛真源后，"目标"与"实际"才都在受控面上。

4. **摘要把"生成态"也算成了内容。** 用 `git archive` 复现机队内容时发现两者差 6 个文件：
   `packages/gateway/data/los.db{,-shm,-wal}`（本地 SQLite 运行态）与
   `packages/web/test-results/**`（Playwright 产物）—— 而这两类**仓库的 `.gitignore` 早已声明
   不是内容**（`*.db*`、`packages/<pkg>/test-results/`），只是摘要没有照做。后果有两层：
   网关跑一次测试、或本地库写一次 WAL，**目标摘要就自己移动**（与代码无关的漂移）；而且这
   428 KB 会被下发到每一台节点。已按 `.gitignore` 的类排除，并从打包里去掉（节点上的旧副本由
   剪枝清掉）。**这也是"载荷可从一个修订复现"的前提** —— 在此之前 `git archive` 永远对不上机队。
5. **模块的入口判据在符号链接路径下静默失效。** 它用字符串比较 `argv[1]` 与 `import.meta.url`，
   路径只要经过符号链接（macOS 的 `/tmp` 就是链接）就不相等 ⇒ **空输出、退出码 0**；
   而 `los.sh` 的兜底会把它显示成 `0.1.0`（看起来像个正常版本号）。实测于把载荷解到 `/tmp` 后
   调用它。已改为 realpath 比较，并让 `los.sh` 在"算不出来"时**大声告警**而不是静默给 base，
   另加一条经符号链接调用的回归测试。

6. **"本机节点跑工作树"本身就是个特殊化，已消除。** `mbp-executor-1` 之前从网关的**可编辑
   checkout** 运行：身份 = "编辑器此刻的样子"；`tsx` 首次 require 才从磁盘读模块 ⇒ 未提交改动
   **不必重启**就能进入执行路径；而且滚动它要 `los.sh restart`，连网关一起弹。更关键的是它是
   **最忙**的节点（近 7 天 282/389 个任务，72%），于是"判据比事实弱"在这台上代价最大。
   现在它与 M3 **配置完全一致**：同一棵钉树 `~/.local/share/los`、同一个 launchd 标签、
   同一个驱动（`tools/deploy-drivers/macos-launchd.sh`），只差传输（`local` vs ssh）；
   钉树由同一份**冻结载荷**喂，滚动只重启执行器（网关留在 checkout 上继续跑）。
   代价：改了 los 代码要显式滚一次才对本地任务生效；好处：这台不再执行半成品代码，
   plan 里那个"恒 off-target 的幽灵节点"也消失了（探针改为读钉树）。

## 6. 第二阶段（本次只设计、不实现）：节点心跳自报摘要

现状下"这台收敛了吗"要逐台 SSH 探测（plan 是 O(节点数) 次远程调用，Windows 还探不了）。
把摘要提升为一个**节点自报的观测事实**：

- 执行器在心跳里带 `contentDigest`（D 落地后，节点本地一算即得，成本 ~30 ms）；
- 注册表加一列（迁移），心跳写入；
- `--plan` 直接读库 → **一次查询代替 N 次 SSH**；"已收敛"不再要求"能 SSH 到节点"。

前置与门禁（否则会造出新的假阳性）：
- 必须等 D 落地（节点得先能算摘要）；
- 摘要缺失或比心跳陈旧时，plan 必须报 `unknown`，**不得**当作"已收敛"；
- 摘要与 `target_version` 分属"实际态/期望态"，不许互相推导；
- 期望态取自**已合并的修订**（见 §5.2 第 3 条），并保留"工作树不得领先于修订"的显式闸门。


## 7. 与已修两个缺陷的关系

M3 的剪枝（GNU-only `xargs`）与 Windows 的 verify（三条断言对崩溃循环全成立）都不是本文要修的
东西，但三者是同一族：**判据比事实弱**。本文把这一族的根因收敛成一句可执行的规则：

> 标识必须由**一个可复用的单一实现**产生，并且**每个平台都能算**；
> 只能在一个平台算出来的判据，等于没有判据。
